**做了**：见 [decisions.md](./decisions.md) D32（分区依据与三处判断）、D33（选项少的一律平铺成按钮组）。

## 第二轮 · 首位用户（布局微调）

**诉求**

1. 玩具盒改为**左边缘竖排工具条** —— 点顶栏「玩具盒」在画布左缘展开竖排图案按钮
   （缩略图 + 名称），选中态高亮，再点收起；**简洁模式常驻展开**。世界卡片维持顶部横条不变。
2. 顶栏运行控件（播放/暂停、单步、速度）移到**右段**，**清空留左段**，
   模式/语言/「?」仍在最右角。
3. 纯 UI 层，零新词条，窄屏约束照旧。

**理解**

- 第 1 条把两类"挑东西"分到了两条边：**图案是高频、要反复取用的**（画一个、再画一个），
  放在左缘竖排既常驻又不占顶部高度；**世界是低频的整体切换**，横条一次看完五个再收起。
  两者不再互斥 —— 它们占的是不同的边，可以同时开着。
- 第 2 条把"运行"和"重来"分了开：播放/单步/速度是**连续调节的一组**，
  挪到右段和模式/语言凑在一起，手不用在顶栏两端来回跑；
  清空是**破坏性的一次性动作**，单独留在左段，离得远反而不容易误按。

**做了**

- 左缘工具条 `#tool-rail`：竖排图案按钮（SVG 缩略图 + 名称），选中态沿用原来的 `.card.on` 高亮；
  它是工作区的一个**布局成员**而不是浮层，所以展开时画布变窄、绝不会被盖住。
- 简洁模式进入时强制展开工具条，并把「玩具盒」标签本身隐藏（`data-mode="full"`）——
  常驻展开的东西不需要开关。
- 顶栏改为：品牌 / 清空 ‖ 玩具盒 · 世界 ‖ …… ‖ 播放 · 单步 · 速度 ‖ 模式 · 语言 · ?
- 零新词条：工具条的名称与提示沿用 `pattern.<key>`、`pattern.<key>.desc`、`pattern.hint`。

提交见下方 git 记录。

## 第三轮 · 首位用户（随机初始化按钮"没反应"）

**诉求**：完整模式、B3/S23、密度 0.3、种子留空，点「随机初始化」棋盘无任何变化，
随后播放报第 1 代全灭。怀疑布局重构后按钮事件绑定断了。

**查下来：绑定没断，但确实是布局重构引入的问题，而且是两个叠在一起的**

先按字面复现：真实点击「随机填充」，种子回填、活细胞 11997、提示条正常 —— 绑定完好。
又查了重复 id（无）、`elementFromPoint`（没有元素盖住按钮）、`disabled`/`readOnly`（都正常）。
于是回头查布局重构改动的结构本身，找到两处：

**A. 三个按钮组被包在 `<label>` 里（破坏性）**

点 `<label>` 的文字或留白，浏览器会把「激活」转发给它里面第一个可关联控件。
尺寸/边界/色带三组按钮当时都写在 `<label class="field">` 内，于是：

- 点标题「尺寸」两个字 = 点了「100 × 100」→ `engine.resize()` **把整盘棋静默清空**
- 点「边界」= 悄悄切回环形；点「色带」= 悄悄切回翠绿

实测点一下「尺寸」两字：棋盘从 200×200 变成 100×100，活细胞 14127 → **0**。
用户"棋盘空了 → 播放报第 1 代全灭"的后半段就是这么来的。
按钮组本身写得没错（直接点按钮是对的），错在外面那层 `<label>`。

**B. 开机预填了种子框**

装配阶段有一行 `app.el.seed.value = '4271'`。规格阶段 1 写的是
「种子输入框，**留空则随机生成种子并显示**」——空 = 换一张新盘。预填之后，
第一次点「随机填充」会用同一个种子重放出**一模一样的棋盘**，看上去就像按钮没反应。
用户"点了棋盘无任何变化"的前半段就是这么来的。

**做了**

- A：三个按钮组从 `<label>` 换成 `<div class="field">`，标题用 `.field-label`，样式不变
- B：删掉开机预填；种子框以占位符起步，开机这局的种子在编年史「开局」一条里仍有记录

**补了三条接线守卫**（静态扫描源文件，两个运行器都跑）

1. `index.html` 里任何 `<label>` 都不许包 `<button>`
2. 代码里 `getElementById('x')` 引用的 id 必须在 `index.html`（或代码自己 innerHTML 造出来的节点）里存在
   —— 这条守的是"元素被搬走/改名，绑定悄悄落空"这一整类重构事故
3. 种子框开机必须是空的，且 `main.js` 不许在装配阶段给它赋值

三条都做过变异验证：把 bug 装回去，测试立刻变红。

**顺带说明一个不是 bug 的现象**：种子框里已经有值时再点「随机填充」，会得到完全相同的棋盘。
这是规格要的确定性（同种子同密度 ⇒ 逐格相同），不是故障。想换一张就把种子框清空。

## 第四轮 · 首位用户（界面微调 + 流程修正）

**诉求**

1. 清空按钮改红色（danger），hover 加深，位置暂不动
2. 所有按钮组统一"选中高亮、未选中灰底"；世界卡片与玩具盒的选中态同步加强
3. 顶栏或 HUD 常驻显示当前世界名，避免切去烟花世界玩过之后忘了切回来
4. 流程修正：acceptance.md 的打勾要在 commit 前单独确认

**理解**

第 3 条指向一个真实的迷路场景：世界一换，同样的图案长出来的东西完全不同，
而"我现在在哪个世界"这件事之前只写在**完整模式**侧栏的规则分组里 ——
简洁模式下根本看不到。所以它该进 HUD（两种模式常驻），而不是再加一个面板。

第 4 条是我的流程问题，不是界面问题：阶段 3 与阶段 4 各出过一次
"改 acceptance.md 的补丁没匹配上、但同一条命令里的 commit 照常执行"，
两次都靠事后 amend 补。amend 补救不算数 —— 提交历史里那一版本身是错的。

**做了**

- 清空按钮加 `.danger`（暗红底 / hover 加深），位置不动
- 三处"一组里选一个"的控件（侧栏按钮组、顶栏分段开关、顶栏标签）此前样式各写各的，
  现在统一成一条规则：未选中灰底灰字、选中绿底亮字加粗
- 卡片选中态加强：描边 + 底色 + 标题变色；工具条的卡片再加一条左侧竖杠，
  世界卡片右上角加一个小圆点
- HUD 增加常驻的「世界 ⟨名字⟩」，用强调色；自定义规则显示「自定义规则」。
  判定沿用规则指纹比对（D25），所以在编辑器里手搓出等价于 Seeds 的规则也会显示「烟花世界」
- 流程规矩写进 acceptance.md 抬头：**先改文件 → 单独 `git diff` 看一眼 → 再 commit**，
  不把两者串在同一条命令里

全部沿用现有词典键（`world.section` / `world.<key>` / `rule.custom`），零新增文案。

## 第五轮 · 首位用户（读档后画面与统计归零）

**诉求**：读档硬指标通过（代数、存活、格局一致），但所有细胞显示为新生白色，
年龄着色、统计面板、人口折线全部归零 —— 重放显然没经过视觉状态和数据记录层。
评估能否在重放时顺路推进；若对长局速度影响明显，说明取舍。
另问：进度条在短局一闪而过是否预期，可考虑一秒内完成的干脆不弹。

**诊断**：确实如此。`applySave` 直接 `engine.step()` 逐代跑，绕过了
`visual.advance`（年龄/余晖）、`records.onGeneration`（快照/编年史）、`series.push`（折线）。
读档后 `visual.sync()` 把年龄一律重置成 1，于是满屏新生白。

顺带查出一个更严重的：**画笔没有标记 runDirty**。手绘过的局会被当成纯种子局存档，
读档时按种子重放 —— 棋盘必然对不上。贴图案和导入 RLE 标了，唯独画笔漏了。

**做了**

重放改成走**和正常运行完全相同的那条流水线**：先换上引擎，再逐代
`engine.step → series.push → records.onGeneration → visual.advance`。

两处不照搬：

1. **年龄只补跑最后 80 代。** 年龄色阶在第 64 代就封顶（`AGE_MAX`），
   活过 64 代和活过 600 代渲染出来是同一个颜色。所以从"最后 80 代"处
   `visual.sync` 再逐代推进，渲染结果与从头跑满**逐格相同**，代价却从 O(总代数×棋盘)
   降到 O(80×棋盘)。有测试钉住这条等价性，并附一个反例（预热只有 8 代时会露馅）。
2. **重放期间不做终止判定。** 省掉每代一次全盘哈希；也避免"存档正好落在循环里"时
   重放到一半弹出总结卡片。重放结束后把当前棋盘补进查重表，之后的循环检测照常接上。

**取舍数据**（200×200 重放 2000 代）

| 做法 | 耗时 | 相对裸跑 |
| --- | --- | --- |
| 裸跑（改之前） | 212–231ms | — |
| **顺路记账 + 年龄预热窗口（采纳）** | **215–216ms** | **−7% ~ +11%，在测量噪声内** |
| 顺路记账 + 每代都推进年龄 | 317ms | +37% |
| 再加每代算棋盘哈希 | 381ms | +65% |

所以你的判断是对的：增量成本可以忽略。前提是那两个优化 —— 直接照搬全套流水线要多花三成半。

**实测结果**：614 代的局，存档前后
棋盘哈希、年龄分布（含 65+ 档 534 个）、统计六项、折线点数、快照条数、编年史条数**逐项完全一致**。

**进度条**：短局一闪而过不是预期，已按你的建议改。判据不是"代数超过多少"，
而是跑完第一片后按**实测速度外推总耗时**，超过 1 秒才弹 ——
500×500 的两千代和 100×100 的两千代不是一回事，写死代数阈值是错的。
判据抽成了纯函数 `shouldShowProgress()` 以便直接测。

**顺带**：手绘局的存档基线改在**每次编辑动作结束时**抓（抬笔、放下图案），
而不是存档那一刻。这样存档里还留着"最后一次编辑之后"那段可重放的代数，
读档后年龄和统计才回得来；否则重放 0 代，什么都恢复不了。
